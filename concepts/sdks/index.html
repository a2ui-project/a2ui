SDKs

Official A2UI SDKs are organized into three layers:

  • Core SDK for shared protocol models and surface state.
  • Agent SDK for catalog-driven prompt generation and model output compilation.
  • Renderer SDK for mounting surface state in a client UI framework.

Both the Agent SDK and the Renderer SDK build on their language’s Core SDK, so server-side validation and client-side message resolution share one implementation per language. Client-server applications typically pair two layers on each side of a network boundary, such as a Python agent server communicating with a SwiftUI or Jetpack Compose client. Codebases that handle both model inference and UI rendering in the same language, such as TypeScript web apps or Dart and Flutter apps, can use all three layers together in one project.

Core SDK

Every Agent SDK and Renderer SDK depends on its language’s Core SDK, which implements the protocol data structures, reactive state containers, and expression evaluators common to agents and clients.

Primary functions

  1. Parses and serializes A2UI wire messages across supported protocol versions (v1.0, v0.9.1, and v0.8 in TypeScript and Python).
  2. Loads Catalog JSON Schemas and validates component hierarchies, placement constraints, and message payloads.
  3. Maintains per-surface component graphs and JSON data model state while applying incremental updates by component ID and JSON Pointer path.
  4. Evaluates data bindings, collection templates, string interpolation expressions, function invocations, and validation checks.

To implement a Core SDK in another language, read blueprints/modules and validate against the YAML suites in conformance/core.

Agent SDK

An Agent SDK connects a language model or agent runtime to the A2UI protocol while leaving model selection, tool execution, and conversation state under your application’s control.

Primary functions

  1. Negotiates active Catalog definitions and protocol versions (v0.9.1 and v1.0) against the capabilities reported by the client renderer (see Overview).
  2. Generates skills, system prompt instructions, and examples directly from catalog schemas and prompt instructions, replacing hand-written prompts that become outdated when components change.
  3. Compiles streaming or batch model output from inference formats (such as compact Express syntax, which cuts output tokens without client changes, or chunk-healed Direct JSON) into standard A2UI wire messages.
  4. Validates outgoing messages statefully against active surface state on the server so broken component IDs, placement violations, or schema mismatches can be fed back to the model for self-correction before transmission.
  5. Supports optional server-side @macro expansion in Python and integrates with agent frameworks and transports including Google ADK and the A2A protocol.

Go and community SDKs

For Go services and CLI clients, community-maintained libraries cover server-side validation, streaming parsers, and terminal rendering—including satorunooshie/a2ui-go, tmc/a2ui, charmbracelet/a2tea, and muncus/a2term (listed with version details in Community Projects).

To implement a conformance-verified Core or Agent SDK in Go, Rust, C#, or another language, follow the language-agnostic specifications in blueprints/modules, verify behavioral parity against the YAML suites in conformance/core and conformance/agent, and open a pull request to add your package to Community Projects.

See Using a catalog in an agent and Inference Formats for TypeScript, Python, and Dart examples of configuring A2uiGenerator, negotiating capabilities, and compiling model responses, or run a working agent in the Quickstart.

Renderer SDK

A Renderer SDK connects a Core SDK’s resolved surface state to a client UI framework. Official Renderer SDKs include a built-in implementation of the Basic Catalog styled through the host framework’s theming system, and let you register custom catalogs with per-component rendering logic and local functions (see How to Define a Catalog).

Primary functions

  1. Applies incremental surface, component, and data model updates across supported protocol versions (v0.9.1, v1.0, and v0.8 on Web), updating only changed subtrees so unchanged siblings keep focus and local UI state.
  2. Evaluates reactive data bindings, nested collection scopes, relative JSON Pointers, and local two-way input edits.
  3. Executes local catalog functions and reactive validation checks, enforcing v1.0 caller and user-activation rules.
  4. Builds capability and data-model sync metadata payloads for your transport layer, dispatches user action events and structured error messages, and handles v1.0 bidirectional function RPCs.
  5. Maps protocol accessibility attributes to host accessibility APIs across Flutter, Web WAI-ARIA, SwiftUI, and Jetpack Compose.
