How to Integrate A2UI into an Agent

Integrate A2UI into an agent using the Agent SDKs to stream validated interactive surfaces to clients and respond to user actions across turns.

For the client side, see How to Integrate A2UI into a Client. If your agent and renderer live in the same binary or codebase, combine both guides, skip the transport step, and pass messages directly from agent output into the rendering pipeline (the Agent and Renderer SDKs share the same Core SDK data structures). To register custom widgets beyond the built-in Basic catalog, see How to Define a Catalog, and for trade-offs between inference formats see Inference Formats. Agent SDKs are available for TypeScript, Python, and Dart, while Swift and Kotlin target client-side rendering (see SDKs).

Install the Agent SDK and Core SDK packages for your language:

Step 2: Initialize the A2UI generator

Create a shared generator configured with your component catalogs, your chosen inference format, and a session map to track active surface state across turns.

The steps below use an illustrative OrderAgentService class representing your application’s own domain service rather than an A2UI SDK class. Register the built-in v1.0 Basic catalog (and any custom domain catalogs) at startup, and inject a model-streaming callback so the service stays decoupled from any specific LLM client or transport. The generator also configures the inference format: Express (ExpressFormatFactory) is the default, instructing the model to emit compact <a2ui> blocks that compile into validated A2UI messages, and can be swapped for other formats such as Direct JSON (see Inference Formats):

  • TypeScript
  • Python
  • Dart

Step 3: Build the system prompt and stream A2UI messages

On each conversation turn, generate the A2UI system prompt instructions for the session and stream the language model’s token output through a request processor to emit validated A2UI messages.

Look up or initialize the session’s renderer state, create a request processor for your registered catalogs (or negotiate client capabilities per request when serving external clients) bound to that state, and append its generated prompt snippet to your agent’s role instructions. When reusing session state across turns, instruct the model to pass update=true (surface("id", update=true)) when modifying an existing surface so follow-up turns update the active surface in place rather than attempting to recreate it. If each chat turn creates an independent surface instead, omit the session state so every response validates from an empty state.

As tokens arrive from the language model, feed each chunk into the processor’s stream and close the stream when generation finishes. Stream parts carry either conversational prose (text parts, omitted in the UI-only generator below) or A2UI payloads: the stream reader closes partial string properties such as text incrementally as tokens arrive, updates the session state, and yields Core SDK AgentToRendererMessage structures (createSurface, updateComponents, updateDataModel, and deleteSurface) as soon as they are ready:

  • Python
  • Dart

Step 4: Process messages from the renderer

Handle incoming A2UI messages from the client renderer with RendererToAgentMessageProcessor, prompting the model on user actions and handling other messages with deterministic logic.

Separate plain text inputs from A2UI renderer_to_agent messages at your transport boundary: text messages always prompt the model directly through your turn runner, whereas A2UI messages go through your renderer message handler. Register an action callback on RendererToAgentMessageProcessor that forwards action events to the turn runner, while deterministic logic handles callAgentFunction RPCs (see Register agent-hosted functions) and client error reports:

  • Dart

Step 5: Connect to a transport

Connect your agent service to the transport channel your application uses to exchange messages with clients, or pass messages directly to a local renderer when running in the same process.

A2UI is transport-agnostic: an agent can exchange JSON envelopes over Server-Sent Events (SSE), WebSockets, HTTP streaming responses, gRPC, or standardized agent protocols such as AG-UI, A2A, and MCP (covered in Connect to agent frameworks and transports). Whichever transport you choose, separate plain text messages from A2UI messages: pass text prompts directly to your turn runner, pass A2UI envelopes to your renderer message handler, and serialize each emitted AgentToRendererMessage onto your outbound channel.

Additional steps

Negotiate client capabilities

Negotiate active catalogs per request when your agent serves external clients or multiple shipped app versions with different widget sets.

If your team owns both the agent and the client app, targeting your known catalogs directly as in Step 3 avoids runtime capability plumbing. Otherwise, register every catalog your agent supports on the generator, read metadata.a2uiRendererCapabilities (or metadata.a2uiClientCapabilities for v0.9.1 clients) on each request, and verify that the negotiated processor accepts the existing session state in case the caller’s catalogs changed. In TypeScript and Python, all catalogs on a single generator must target the same protocol version, so maintain a separate v0.9 generator when serving both v1.0 and v0.9.1 clients (Dart groups mixed-version catalogs automatically):

  • TypeScript
  • Python
  • Dart

Client renderers attach their supported capabilities in transport metadata (a2uiRendererCapabilities under "1.0" in v1.0, or a2uiClientCapabilities under "v0.9" in v0.9.1):

Register agent-hosted functions

Attach AgentFunction handlers to your catalog to run deterministic server-side operations without an LLM round-trip.

Use AgentFunction for deterministic backend work (such as database updates, pricing rules, or order lookups) rather than branching on action event names. Attach your agent functions to the catalog before passing it to A2uiGenerator and RendererToAgentMessageProcessor in Step 4; incoming callAgentFunction messages (v1.0 only) validate arguments against the function schema and return an agentFunctionResponse automatically:

Non-streaming generation and validation retry

Buffer complete model responses before sending messages when you want atomic validation and clean-slate retries instead of progressive streaming.

In Step 3, openStream() (open_stream() in Python) validates component schemas and surface topology incrementally as tokens arrive. Because progressive messages have already reached the client when a streamed block fails, recovering mid-stream means flushing err.partialResults (err.partial_results in Python), opening a new openStream() on the same RendererState, and either repairing existing surfaces in place (surface("id", update=true)) or sending deleteSurface before regenerating.

When your agent uses buffered (non-streaming) LLM calls instead, pass the full model text to parseResponse (parse_response in Python). If a block invents an unknown component, omits root, or leaves a dangling child ID, parseResponse rolls back RendererState and raises an A2uiError so you can pass the failed output and error message back to the model on a retry turn:

  • TypeScript
  • Python
  • Dart

Customize catalogs, examples, and inference formats

Prune large catalogs, attach few-shot A2UI JSON examples, or customize inference format options on the generator to steer layout quality and reduce prompt size.

Attach component or function pruning transformers to CatalogConfig to expose only the widgets a workflow needs, and pass canonical A2UI JSON example turns to A2uiGenerator, which validates them against the negotiated catalogs and decompiles them into the active inference format (such as <a2ui> blocks in Express). You can also pass options to ExpressFormatFactory or swap to DirectJsonFormatFactory when a model emits raw JSON inside <a2ui-json> tags (see Inference Formats). In Python, compose server-side component templates with @macro and MacroExpander so clients render new composite layouts without a client release (see Using Macros):

Connect to agent frameworks and transports

Plug the A2UI generator and message processors into standard agent frameworks and protocols instead of writing custom transport plumbing.

Google ADK

Use the ADK integration package to manage per-session request processors, inject A2UI prompt instructions without colliding with ADK {variable} state templating, expose the client A2UI toolset, and bridge A2A events and function RPCs:

Avoid raw prompt strings in LlmAgent.instruction

ADK substitutes {name} placeholders in plain string instructions from session state. Concatenating processor.prompt_snippet into a raw LlmAgent.instruction string raises KeyError on A2UI braces (such as ${expression} or \p{XID_Start}). Always wrap your instruction in A2uiInstruction, which resolves your own {store_city} template variables while leaving the A2UI prompt untouched.

AG-UI and CopilotKit

Enable A2UI on CopilotRuntime to stream A2UI surfaces over AG-UI across Python and TypeScript agent backends.

When injectA2UITool: true is set (or when the frontend supplies a catalog), CopilotKit injects the A2UI generation tool and translates tool calls and state deltas into AG-UI events across integrations including Google ADK (ag_ui_adk), LangGraph (CopilotKitMiddleware), and AWS Strands (@ag-ui/aws-strands).
