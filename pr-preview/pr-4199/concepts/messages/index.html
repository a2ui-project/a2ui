Messages

A2UI agents and client renderers communicate by exchanging asynchronous JSON messages in both directions to manage UI surfaces and handle user interactions. These message types can be sent over a variety of transports, including Agent-to-Agent (A2A) and Model Context Protocol (MCP).

Alongside explicit A2UI messages, implementations can use metadata to include renderer context in requests sent for other purposes. For example, when a user sends a text prompt, the renderer can attach its supported catalogs or synchronized surface state to the outgoing request.

Agent-to-renderer messages

Agent-to-renderer messages construct surfaces, update component hierarchies and reactive data models, clean up surfaces, invoke client-side functions, and return results for agent-side function calls. Each wire message in either direction is a JSON object with a "version" field ("1.0" in v1.0, or "v0.9" / "v0.9.1" in v0.9.1) and a single message key.

createSurface

v1.0 agent_to_renderer.json #CreateSurfaceMessage ↗ v0.9.1 server_to_client.json #CreateSurfaceMessage ↗

The createSurface message allocates a new UI surface identified by surfaceId. The surfaceId must be globally unique within the rendering context (the MessageProcessor instance on the renderer), which is typically a conversation. Creating a surface implicitly instantiates the reserved Surface container component with child: "root". In v1.0, createSurface can also include optional surface-level custom extensions under metadata.extensions (Extensions).

Properties

PropertyTypeRequiredDescription
surfaceIdstringYesUnique identifier for the surface.
catalogIdstringOptional (v1.0), Yes (v0.9.1)Default catalog identifier for this surface (for example, travel:flights). In v1.0, individual components (@catalogId) and function calls (catalogId) can specify their own catalog when omitted here.
sendDataModelbooleanOptionalWhen true, the renderer attaches the full surface data model in transport metadata (a2uiRendererDataModel in v1.0 / a2uiClientDataModel in v0.9.1) on every message to the creating agent.
componentsarrayOptional (v1.0)Initial flat list of component definitions, allowing single-message surface creation.
dataModelobjectOptional (v1.0)Initial root data model JSON object for the surface.
metadataobjectOptional (v1.0)Surface-level extensions container with optional extensions (Extensions).

Changes in v1.0

In v1.0, catalogId is optional, components and dataModel can be passed inline to initialize a surface in a single message, and the v0.9.1 theme property is removed in favor of host application styling.

updateComponents

v1.0 agent_to_renderer.json #UpdateComponentsMessage ↗ v0.9.1 server_to_client.json #UpdateComponentsMessage ↗

The updateComponents message adds or replaces component definitions in an existing surface. Relationships between components are expressed by ID references in a flat adjacency list rather than nested JSON trees, and one component in the surface must have id: "root". In v1.0, individual component definitions in components can also carry optional component-level extensions via @metadata.extensions (ComponentCommon).

Properties

PropertyTypeRequiredDescription
surfaceIdstringYesIdentifier of the surface to update.
componentsarrayYesNon-empty flat array of component objects. Components whose id already exists in the surface replace the stored definition.

updateDataModel

v1.0 agent_to_renderer.json #UpdateDataModelMessage ↗ v0.9.1 server_to_client.json #UpdateDataModelMessage ↗

The updateDataModel message updates the surface data model at a targeted location using an RFC 6901 JSON Pointer, allowing the agent to refresh bound values without resending component definitions.

Properties

PropertyTypeRequiredDescription
surfaceIdstringYesIdentifier of the target surface.
pathstringOptionalRFC 6901 JSON Pointer indicating where to apply the update (for example, "/selectedFlight"). When omitted or set to "/", the update replaces the entire data model.
valueanyYes (v1.0), Optional (v0.9.1)Value to store at path.

Key deletion version delta

In v1.0, value is required; set "value": null to delete the key at path. In v0.9.1, value is optional, and omitting value removes the key at path.

callRendererFunction (v1.0 only)

v1.0 agent_to_renderer.json #CallRendererFunctionMessage ↗

The callRendererFunction message is an agent-initiated remote procedure call (RPC) that directs the renderer to execute a catalog function registered on the client (for example, reading device timezone or screen dimensions). Only catalog functions declaring allowedCallers as "agentOnly" or "rendererOrAgent" may be called by the agent.

New in v1.0

callRendererFunction is introduced in protocol v1.0. In v0.9.1, server_to_client.json does not define an agent-to-renderer function invocation message.

Properties

PropertyTypeRequiredDescription
functionCallIdstringYesUnique correlation identifier for this call, copied verbatim into rendererFunctionResponse.
callFunctionobjectYesFunctionCall object with required @call, required catalogId, and optional args.
surfaceIdstringOptionalSurface ID whose data model provides the evaluation context. When omitted, the function executes in an isolated root context with {}.

Renderer-to-agent messages

Renderer-to-agent messages report user interactions, invoke remote functions on the agent, and return results from agent-initiated client function calls.

v1.0 renderer_to_agent.json ↗ v0.9.1 client_to_server.json ↗

action

v1.0 renderer_to_agent.json #action ↗ v0.9.1 client_to_server.json #action ↗

The action message notifies the agent that the user triggered an event action on an interactive component (such as clicking a Button configured with action.event). Before dispatching the message, the renderer resolves any data bindings inside action.event.context and action.event.userMessage against the local data model. In v1.0, action can also include optional renderer-side custom extensions under metadata.extensions (Extensions).

Properties

PropertyTypeRequiredDescription
namestringYesEvent name declared on the component’s action.event.name.
surfaceIdstringYesSurface ID where the interaction originated.
sourceComponentIdstringYesComponent id that triggered the action.
timestampstringYesISO 8601 date-time string indicating when the event occurred.
contextobjectYesResolved key-value dictionary from action.event.context with all data bindings evaluated to current values.
userMessagestringOptional (v1.0)Human-readable string resolved from action.event.userMessage, suitable for adding to LLM conversation history.
metadataobjectOptional (v1.0)Action-level extensions container with optional extensions (Extensions).

Metadata

v1.0 renderer_capabilities.json ↗ v0.9.1 client_capabilities.json ↗ v1.0 renderer_data_model.json ↗ v0.9.1 client_data_model.json ↗

Transport metadata lets the renderer attach A2UI context to outgoing requests sent for other purposes (such as user text prompts in A2A or request metadata in MCP), flowing from the renderer to the agent.

Metadata key (v1.0)Metadata key (v0.9.1)Purpose
a2uiRendererCapabilitiesa2uiClientCapabilitiesAdvertises supported protocol versions, supportedCatalogIds, and optional inlineCatalogs.
a2uiRendererDataModela2uiClientDataModelSends full local data models for active surfaces created with sendDataModel: true.

Renderer capabilities (a2uiRendererCapabilities in v1.0 / a2uiClientCapabilities in v0.9.1) are an optional mechanism that loosely coupled systems can use to negotiate which protocol versions and catalogs can be used when they are not known in advance. Systems where the agent and client are owned by the same party may not need capability negotiation if the protocol version and catalogs are agreed in advance. Agents can also advertise their static catalog support ahead of time via agent_capabilities.json (v1.0) or server_capabilities.json (v0.9.1), such as in an A2A Agent Card.

When any active surface was created with sendDataModel: true, the renderer attaches a2uiRendererDataModel (or a2uiClientDataModel in v0.9.1) on outgoing messages to that agent so local input state stays synchronized without embedding full data models inside action payloads.
