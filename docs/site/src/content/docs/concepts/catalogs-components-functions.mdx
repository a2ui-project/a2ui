In A2UI, an agent never sends arbitrary HTML, CSS, or executable scripts across the wire. Instead, the agent and the client application agree on a **Catalog**: a versioned JSON Schema document that declares the UI components the agent can instantiate, the functions it can invoke, and the design rules it should follow.

When an agent streams a surface, every component node and function call in the payload is validated against the active catalog before the client renderer mounts a single native widget.

## Conceptual Foundations

### 1. Catalogs

A **Catalog** is a formal contract identified by a globally unique `catalogId` (conventionally a URI such as `https://a2ui.org/specification/v1_0/catalogs/basic/catalog.json` or `https://example.com/catalogs/travel/v1/catalog.json`).

A single catalog document serves both sides of the runtime:

- **On the Agent Server**: The Agent SDK (`@a2ui/agent`, `a2ui-agent-sdk`, `a2ui_agent`) reads the catalog's component schemas, function signatures, and markdown `instructions` to synthesize the LLM system prompt and validate outgoing messages as they stream.
- **On the Client Renderer**: The Core SDK (`@a2ui/web_core`, `a2ui_core`, `A2UICore`) pairs the catalog's schemas with native widget implementations (Flutter widgets, React components, Angular components, Lit elements, SwiftUI views, or Jetpack Compose composables) and executable function implementations.

---

### 2. Components

A **Component** definition in a catalog describes the shape and constraints of a single UI building block. Under the `components` map of a catalog JSON document, each entry is a JSON Schema object that defines:

| Aspect | Schema Mechanism | Purpose |
| :--- | :--- | :--- |
| **Discriminator** | `"component": { "const": "FlightStatusCard" }` | Identifies the component type in the flat surface component list. |
| **Dynamic Properties** | `$ref` to `DynamicString`, `DynamicNumber`, `DynamicBoolean`, `DynamicStringList`, or `DynamicValue` | Allows a property to accept a literal value, a reactive JSON Pointer data binding (`@path` / `path`), or a function call (`@call` / `call`). |
| **Child Slots** | `$ref` to `ComponentId` (single child) or `ChildList` (array of child IDs or `{path, componentId}` template) | Connects components into a directed acyclic graph without deeply nested JSON trees. |
| **Hierarchy Constraints** | `"allowedParents": ["Column"]`, `"allowedChildren": ["Text", "Button"]` | Restricts where the component can sit in the layout tree; enforced by the Core SDK topology validator. |
| **Validation Rules** | `$ref` to `#/$defs/Checkable` (`checks` array of `{condition, message}`) | Attaches reactive client-side validation checks to interactive inputs. |
| **Actions** | `$ref` to `common_types.json#/$defs/Action` | Declares what happens when a user interacts with the component (dispatches an `action.event` to the agent or runs a local `action.functionCall`). |

Here is how a custom `FlightStatusCard` component is declared inside a catalog schema:

```json
{
  "FlightStatusCard": {
    "type": "object",
    "description": "Displays live flight status, fare, and boarding actions.",
    "allowedParents": ["Column", "List"],
    "properties": {
      "component": {
        "const": "FlightStatusCard"
      },
      "flightNumber": {
        "$ref": "common_types.json#/$defs/DynamicString",
        "description": "IATA flight designator, e.g. 'NH 105'."
      },
      "fareAmount": {
        "$ref": "common_types.json#/$defs/DynamicNumber",
        "description": "Ticket fare in the booking currency."
      },
      "actionsSlot": {
        "$ref": "common_types.json#/$defs/ChildList",
        "description": "Action buttons displayed in the card footer."
      }
    },
    "required": ["component", "flightNumber"]
  }
}
```

### 3. Functions & Execution Boundaries

Catalog **Functions** provide typed, deterministic logic for formatting values, validating user input, computing boolean conditions, or triggering side effects.

Every function in a catalog declares a `returnType` (`"string"`, `"number"`, `"boolean"`, `"array"`, `"object"`, `"any"`, `"void"`, or `"validationResult"` in v1.0) and a `parameters` (or `properties.args`) schema.

#### Local Client Functions vs. Remote Agent Functions

A2UI separates pure UI evaluation from server-side business logic through two execution targets and two security metadata fields (`allowedCallers` and `requiresUserActivation`):

| Property / Mode | Behavior | Typical Use Cases |
| :--- | :--- | :--- |
| **`allowedCallers: "rendererOnly"`** | Evaluated synchronously or asynchronously inside the client renderer's `MessageProcessor`. Never crosses the network. | Formatting (`formatCurrency`, `formatDate`, `formatString`), input validation (`required`, `regex`, `numeric`), boolean logic (`and`, `or`, `not`). |
| **`allowedCallers: "agentOnly"`** | Executed on the agent server when the client dispatches a `callAgentFunction` RPC message and awaits `agentFunctionResponse`. | Checking live seat inventory, calculating dynamic tax rates, or querying server state without triggering a full LLM turn. |
| **`allowedCallers: "rendererOrAgent"`** | Can be invoked either locally on the client or remotely via RPC. | Shared domain utilities or cross-environment validators. |
| **`requiresUserActivation: true`** | Can only execute in direct response to an active physical user gesture (such as a button tap). | Opening external browser tabs (`openUrl`), triggering native OS share sheets, or requesting device permissions. |

<Aside type="caution" title="Implicit Fallback Routing for Unregistered Functions">
Per the v1.0 specification (`§callAgentFunction`), when a component invokes a function that is **not** registered in the client renderer's local function table, the renderer automatically falls back to dispatching it over the network as a `callAgentFunction` RPC to the agent. Ensure all local formatting and validation functions are registered in your client `Catalog` so a misspelled function name does not trigger an unintended network round-trip.
</Aside>

## Working with Catalogs Across SDKs

### Agent Side: Loading, Deriving, and Pruning Catalogs

On the agent server, you load a catalog from a JSON file (or construct one in code) and pass it to `CatalogConfig`. You can also derive a specialized catalog using `Catalog.derive(...)` or restrict which components and functions the LLM sees for a specific task using `ComponentPruningTransformer` and `FunctionPruningTransformer`.

<Tabs syncKey="sdk-lang">
  <TabItem label="TypeScript">
```typescript
import { readFileSync } from 'node:fs';
import {
  A2uiGenerator,
  CatalogConfig,
  ComponentPruningTransformer,
  ExpressFormatFactory,
} from '@a2ui/agent';
import { Catalog } from '@a2ui/web_core';

// 1. Load a catalog document from JSON
const rawCatalog = JSON.parse(readFileSync('./catalogs/travel.json', 'utf8'));
const travelCatalog = Catalog.fromJson(rawCatalog);

// 2. Or derive a focused catalog keeping specific components + custom instructions
const checkoutCatalog = travelCatalog.derive({
  catalogId: 'https://example.com/catalogs/travel-checkout/v1/catalog.json',
  components: ['Column', 'Row', 'Text', 'FlightStatusCard', 'Button'],
  functions: ['formatCurrency', 'required'],
  instructions: 'Always display FlightStatusCard above the confirmation Button.',
});

// 3. Configure the Agent Generator with optional pruning transformers
const generator = new A2uiGenerator({
  catalogs: [
    new CatalogConfig(travelCatalog, [
      new ComponentPruningTransformer(['Column', 'Text', 'FlightStatusCard', 'Button']),
    ]),
    new CatalogConfig(checkoutCatalog),
  ],
  inferenceFormatFactory: new ExpressFormatFactory(),
});
```

### Client Renderer Side: Registering Native Widgets & Functions

On the client, a `Catalog` binds each component's schema to a native UI widget builder (`ComponentImplementation`) and each local function's signature to an executable callback (`FunctionImplementation`).

<Tabs syncKey="renderer-framework">
  <TabItem label="Flutter">
```dart
import 'package:a2ui_core/a2ui_core.dart';
import 'package:a2ui_flutter/a2ui_flutter.dart';
import 'package:flutter/material.dart';
import 'package:json_schema_builder/json_schema_builder.dart';

// 1. Bind the FlightStatusCard schema to a native Flutter widget
final flightStatusCard = ComponentImplementation(
  name: 'FlightStatusCard',
  schema: S.object(
    properties: {
      'component': S.string(enumValues: ['FlightStatusCard']),
      'flightNumber': A2uiSchemas.dynamicStringReference(),
      'fareAmount': A2uiSchemas.dynamicNumberReference(),
    },
    required: ['component', 'flightNumber'],
  ),
  builder: (context, node, props, buildChild) {
    final flightNumber = props.string('flightNumber') ?? '';
    final fare = props.number('fareAmount') ?? 0;

    return Card(
      child: ListTile(
        leading: const Icon(Icons.flight_takeoff),
        title: Text('Flight $flightNumber'),
        trailing: Text('\$${fare.toStringAsFixed(2)}'),
      ),
    );
  },
);

// 2. Register components and functions in a client Catalog
final travelCatalog = Catalog<ComponentImplementation, FunctionImplementation>(
  id: 'https://example.com/catalogs/travel/v1/catalog.json',
  protocolVersion: A2uiProtocolVersion.v1_0,
  components: [flightStatusCard],
  functions: BasicCatalog.functions,
);

// 3. Pass the catalog to MessageProcessor and render with A2uiSurface
final processor = MessageProcessor(catalogs: [travelCatalog]);
```

import React from 'react';
import { z } from 'zod';
import {
  Catalog,
  type ComponentApi,
  CommonSchemas,
  createFunctionImplementation,
   BASIC_FUNCTIONS,
} from '@a2ui/web_core';
import { A2uiSurface, createComponentImplementation } from '@a2ui/react';

// 1. Define the component API with a Zod schema
const FlightStatusCardApi: ComponentApi = {
  name: 'FlightStatusCard',
  allowedParents: ['Column', 'List'],
  schema: z.object({
    component: z.literal('FlightStatusCard'),
    flightNumber: CommonSchemas.DynamicString,
    fareAmount: CommonSchemas.DynamicNumber.optional(),
  }),
};

// 2. Bind the ComponentApi to a React (or Angular / Lit) view
const FlightStatusCardImpl = createComponentImplementation(
  FlightStatusCardApi,
  ({ props }) => (
    <div className="flight-card">
      <strong>Flight {props.flightNumber}</strong>
      {props.fareAmount !== undefined && <span>${props.fareAmount.toFixed(2)}</span>}
    </div>
  ),
);

// 3. Optionally define a custom local FunctionImplementation
const formatMiles = createFunctionImplementation(
  {
    name: 'formatMiles',
    returnType: 'string',
    schema: z.object({ miles: z.number() }),
  },
  ({ miles }) => `${miles.toLocaleString()} mi`,
);

// 4. Assemble the client Catalog and mount A2uiSurface
export const travelCatalog = new Catalog(
  'https://example.com/catalogs/travel/v1/catalog.json',
  '1.0',
  [FlightStatusCardImpl],
  [...BASIC_FUNCTIONS, formatMiles],
);

## The Basic Catalog

A2UI provides an official **Basic Catalog** ([`catalogs/basic/v1/catalog.json`](https://github.com/a2ui-project/a2ui/blob/main/catalogs/basic/v1/catalog.json) for v1.0, and [`specification/v0_9_1/json/basic_catalog.json`](https://github.com/a2ui-project/a2ui/blob/main/specification/v0_9_1/json/basic_catalog.json) for v0.9.1) containing 18 general-purpose UI components and 14 standard functions:

- **Layout & Containers**: `Row`, `Column`, `List`, `Card`, `Tabs`, `Modal`, `Divider`
- **Display & Media**: `Text`, `Image`, `Icon`, `Video`, `AudioPlayer`
- **Interactive Inputs**: `Button`, `TextField`, `CheckBox`, `ChoicePicker`, `Slider`, `DateTimeInput`
- **Formatting, Validation & Logic Functions**: `formatString`, `formatNumber`, `formatCurrency`, `formatDate`, `pluralize`, `required`, `regex`, `length`, `numeric`, `email`, `openUrl`, `and`, `or`, `not`

The Basic Catalog serves as a styleable reference catalog for common layouts and input controls. Teams can use its schema directly for general user journeys, or map its components to internal design system components on client renderers.

## Capability Negotiation & Catalog Resolution

At the start of a session or turn, the client advertises the catalogs it can render inside `a2uiRendererCapabilities`:

```json
{
  "version": "1.0",
  "a2uiRendererCapabilities": {
    "supportedCatalogIds": [
      "https://a2ui.org/specification/v1_0/catalogs/basic/catalog.json",
      "https://example.com/catalogs/travel/v1/catalog.json"
    ]
  }
}
```

When the agent creates a surface or renders a component, the client resolves the target catalog using a strict **three-step resolution order**:

1. **Component or Function Override (`catalogId`)**: In v1.0, an individual component object or `@call` expression can specify its own `catalogId` property to pull a component or function from a secondary catalog on the same surface.
2. **Surface Default (`createSurface.catalogId`)**: If the component or function omits `catalogId`, it inherits the `catalogId` declared on the enclosing `createSurface` message.
3. **Resolution Error (`CATALOG_ERROR`)**: If neither the component/function nor `createSurface` specifies a `catalogId` (or if the requested `catalogId` is not registered on the renderer), the processor raises a catalog resolution error. It never guesses or falls back to an arbitrary entry in `supportedCatalogIds`.
