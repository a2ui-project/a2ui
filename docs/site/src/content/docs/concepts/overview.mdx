A2UI lets an AI agent describe an interactive UI as a stream of JSON messages that a client app renders with its own native widgets. Below you'll find the mechanics on each side of the connection, how they fit together, and one request traced from the user's prompt to a button tap.

---

## How agents generate UI

On the server, you configure the [A2UI Agent SDK](/concepts/agent-sdks/) with a [component catalog](/concepts/catalogs/) (`catalog.json`) that describes the UI components and functions available to render on your client. From that catalog, the SDK's skill generator produces an A2UI skill containing prompt instructions and grammar rules. Your agent code and LLM runtime sit outside the SDK: they take the generated A2UI skill alongside your domain tools (such as a flight search API), call the model, and pass its UI output to the SDK's compiler. The compiler parses and validates the content against the catalog, then sends layout ([`updateComponents`](/concepts/messages/)) and data ([`updateDataModel`](/concepts/messages/)) messages over a transport such as AG-UI, A2A, MCP, or WebSockets.

On the client, your app hosts an [A2UI Renderer](/concepts/renderer-sdks/), which draws the UI with native platform widgets inside a region of your screen called a surface. Controls bound to the surface's [data model](/concepts/data-binding/) update state locally as the user interacts with them, and user triggers such as button taps send [`action`](/concepts/actions-and-functions/) messages back to the agent.

While this page focuses on generating UI at request time, A2UI content can also be authored in advance and sent as a static payload (for example, returned from an MCP server via an agent to a client), following a traditional server-driven UI pattern.

## UI generation pipeline detail

The rest of this page traces a flight-booking request through each stage of the pipeline: defining the catalog, generating the skill, prompting the model, compiling and validating the output, and rendering the surface on the client.

### Define the catalog

You define the components and functions your client can render in `catalog.json`. A travel app might pair the basic catalog with domain components such as `FlightCard`. Each component declares its properties with JSON Schema, so the Agent SDK can validate that the model only emits components and properties the client knows how to draw:

### Generate the skill

From `catalog.json`, the Agent SDK's skill generator builds an A2UI skill containing grammar rules for the chosen [inference format](/concepts/inference-formats/) (such as Express) together with component and function signatures derived directly from your catalog:

```text
---
name: a2ui
description: Generates interactive user interface components for user requests.
---

# A2UI Express DSL Output Contract

You must output the user interface using A2UI Express.
...

## Grammar Rules

1. Component constructors can be assigned to variables or nested inline inside parent component arguments:
   ...
   Keyword arguments (`param=value`) and positional arguments with `_` placeholders are supported.
...
6. Data bindings: prefix absolute paths in the data model with '$', e.g., $/user/firstName.
...

## Positional Component Signatures
...
• FlightCard(flightNumber, origin, destination, price, passengers)
  - Description: Displays a flight segment with fare and passenger count.
  - flightNumber: IATA flight designator, such as 'LH 454'.
  ...
```

### Prompt the model

The user types a request in the client app:

> _"Berlin to San Francisco today, and two tickets back on Oct 19."_

Your agent then:

1. Calls its domain tools, for example `searchFlights(from: "BER", to: "SFO", date: "2026-10-12")`, to get flights and prices.
2. Decides that a form with passenger counts is more useful here than a paragraph of text.
3. Loads the generated A2UI skill and prompts the model with the flight data.

### Compile and validate the output

The model streams its answer. Instead of writing wire JSON directly, it can use a compact inference format such as Express:

```text
$/outbound/pax = 1
$/outbound/price = 455
$/return/pax = 2
$/return/price = 970

root = Card(Column([
  FlightCard(flightNumber="LH 454", origin="BER", destination="SFO", price=$/outbound/price, passengers=$/outbound/pax),
  FlightCard(flightNumber="UA 901", origin="SFO", destination="BER", price=$/return/price, passengers=$/return/pax),
  Button(Text("Confirm booking"), variant="primary", action=Event("confirm_booking", {outboundPax: $/outbound/pax, returnPax: $/return/pax}))
]))
```

The Agent SDK compiler processes the stream as it arrives:

1. Parses incoming tokens into an intermediate representation.
2. Validates that each component exists in the catalog and that its properties match the schema, reporting invalid output as soon as it appears.
3. Emits the wire messages: `createSurface` opens the surface on the client, `updateComponents` sends the validated component list, and `updateDataModel` sends the initial data values.

### Render on the client

The client receives the messages over its transport (for example AG-UI, A2A, MCP, or a WebSocket), and the A2UI Renderer:

1. Creates the surface identified by `surfaceId`.
2. Builds the native widgets, starting at the component with ID `root` and following each `child` and `children` reference.
3. Subscribes each bound property (such as `/outbound/pax`) to its path in the surface's data model.
4. Updates local state directly: when the user taps `+` on the outbound passenger count, `FlightCard` writes the new value to `/outbound/pax`, every widget bound to that path updates, and nothing is sent to the agent.
5. Sends user actions: when the user taps _Confirm booking_, the renderer resolves the `context` paths against the current data model and sends an `action` message to the agent.
