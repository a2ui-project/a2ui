# **Express Inference Format Feature Blueprint**

This document specifies the language-agnostic architecture, grammar contracts, compilation semantics, decompiler rules, and conformance criteria for the **Express Inference Format** across all A2UI SDK implementations.

---

## **Requirements & Architectural Principles**

### **1. Core Motivation & Design Goals**

A2UI Express is a compact, model-optimized declarative domain-specific language (DSL) designed for Large Language Models (LLMs) and autonomous agents generating generative user interfaces.

- **Token Footprint Reduction**: Direct JSON serialization produces significant output token overhead (keys, quotes, nested brackets). Express DSL compresses interface descriptions by 55% to 70%, directly reducing model latency and cost.
- **On-Device Model Friendly**: Designed for small edge models (such as Gemma 4 E2B/E4B) with constrained context windows and reasoning budgets.
- **Streaming Line-by-Line Evaluation**: The line-oriented grammar enables streaming parsers to evaluate assignments progressively as newlines are emitted, before the model finishes generation.
- **Full Protocol Parity**: Express compiles down to standard A2UI v1.0 and v0.9.1 wire protocol messages (`createSurface`, `updateComponents`, `updateDataModel`), supporting data binding, client actions, and dynamic list templates.

### **2. Catalog-Agnostic Prompt & Signature Generation**

To ensure language-agnostic extensibility and schema-driven stability:
- Express prompt generators (`ExpressPromptGenerator`) MUST decompose prompt building into:
  - `generate_base_rules() -> String`: Emits the base Express syntax specification, sentinel tags (`<a2ui>`), data path binding rules, and template syntax. Must be completely catalog-agnostic.
  - `generate_catalog_instructions(include_schema, catalog) -> String`: Compiles component definitions and function signatures dynamically from the target `A2uiCatalog` JSON schema into positional constructor signatures (e.g. `Text(text, variant?, color?)`).
  - `generate_examples(catalog, validate) -> String`: Formats few-shot examples for the target catalog.
- Hardcoded catalog-specific string filters, regex patches, or component replacements in prompt generators are strictly prohibited.

### **3. Lexer & Parser Grammar Contract**

- The canonical grammar is defined in ANTLR4 syntax at `specification/inference_formats/express/Express.g4`.
- Enclosure Sentinel Tags: Express code blocks generated by LLMs MUST be enclosed within `<a2ui>` and `</a2ui>` tags.
- Identifiers: Variable names MUST adhere to Unicode Standard Annex #31 (UAX #31), starting with a Unicode letter or underscore, followed by letters, digits, or underscores.
- Reserved Identifiers:
  - `root`: The surface root component entrypoint.
  - `_template`: Reserved helper for dynamic list templates (`_template(path, templateComponent)`).
- Assignments:
  - Component assignment: `varName = ComponentName(arg1, arg2, param=val)`
  - Data model assignment: `$/path/to/key = value_literal`
  - Inline child composition: Components may be nested directly inside parent constructor arguments without top-level variable declarations.

### **4. Compiler & Decompiler Behavioral Contracts**

- **AST Walking & Type Normalization**: `ExpressCompiler` walks the parse tree and normalizes arguments against the catalog schema:
  - Positional arguments map to schema property positions defined by the catalog.
  - Keyword arguments override or supply named properties.
  - Primitive coercion (e.g. string numbers to integer/float, boolean literals).
  - Data binding detection: Expressions starting with `$` are mapped to `{ "$expr": "path", "path": "..." }` or `{ "$ref": "..." }` depending on catalog protocol version.
- **Surface Operations**: Compiles down to standard envelopes:
  - `createSurface`: Surface initialization with `root` component, component dictionary, and initial `dataModel`.
  - `updateComponents`: Incremental component updates.
  - `updateDataModel`: Dynamic state changes.
- **Decompilation Parity**: `ExpressDecompiler` translates standard A2UI JSON envelopes back into compact Express DSL, ensuring round-trip idempotency.

## **API Specification**

Every language SDK implementing the Express Inference Format MUST expose the following canonical contracts:

### **1. `ExpressFormat` (`InferenceFormat`)**

```typescript
interface ExpressFormat extends InferenceFormat {
  catalog?: A2uiCatalog;
  surfaceId: string;
  version: string; // "v1.0" | "v0.9.1" | "v0.9"

  promptGenerator: ExpressPromptGenerator;
  parser: ExpressParser;
}
```

### **2. `ExpressCompiler`**

```typescript
class ExpressCompiler {
  constructor(catalog: A2uiCatalog, surfaceId?: string, version?: string);
  compile(dsl: string): Array<A2uiMessage>;
}
```

### **3. `ExpressParser` (`Parser`)**

```typescript
class ExpressParser implements Parser {
  constructor(catalog: A2uiCatalog, surfaceId?: string, version?: string);
  hasFormatContent(content: string, options?: { complete?: boolean }): boolean;
  unwrap(content: string): Array<ResponsePart>;
  compile(dsl: string): Array<A2uiMessage>;
  decompile(messages: Array<A2uiMessage> | A2uiMessage): string;
}
```

### **4. `ExpressPromptGenerator` (`PromptGenerator`)**

```typescript
class ExpressPromptGenerator implements PromptGenerator {
  constructor(format: ExpressFormat);
  generateBaseRules(): string;
  generateCatalogInstructions(includeSchema?: boolean, catalog?: A2uiCatalog): string;
  generateExamples(catalog?: A2uiCatalog, validate?: boolean): string;
  generate(options?: PromptOptions): string;
}
```

## **Conformance Verification**

All implementations of the Express Inference Format MUST pass the following language-agnostic conformance test suites:

1. **Agent Express Conformance**:
   - `conformance/agent/express/prompt_generator.yaml`: Validates base rules and catalog instruction generation.
   - `conformance/agent/express/response_parser.yaml`: Validates tag unwrapping, compilation, and error handling.
2. **Inference Format Conformance**:
   - `conformance/inference_formats/express/compile.yaml`: Validates DSL -> standard JSON message compilation.
   - `conformance/inference_formats/express/decompile.yaml`: Validates standard JSON -> DSL decompilation.
   - `conformance/inference_formats/express/round_trip.yaml`: Validates end-to-end bidirectional fidelity.
